Пароль или API-ключ попал в коммит и уже улетел на GitHub. Разбираемся, как убрать файл из индекса, оставив его на компьютере, и почему скомпрометированный ключ придётся сменить.

Урок 19. Секреты в репозитории

NOTE Зачем это нужно?

Секрет, попавший в коммит, остаётся в истории даже после удаления файла. Сначала нужно отозвать ключ, а уже потом чистить индекс и историю.

Сначала — смените ключ

Если секрет уже оказался в репозитории, считайте его раскрытым. Даже после удаления файла он остаётся в старых коммитах: любой, кто склонирует проект, увидит его через git log -p.

Боты сканируют публичные репозитории за минуты. Поэтому первое действие — отозвать ключ в сервисе и выпустить новый. Чистка истории нужна, чтобы секрет не попал в чужие клоны, но утечку она уже не отменяет.

Убрать из индекса: git rm --cached

git rm --cached файл убирает файл из индекса и оставляет его на диске. Для Git это выглядит как удаление: в следующий коммит попадёт «файла больше нет», а сам файл останется в рабочей папке.

Всё дело во флаге --cached: он трогает индекс, а не вашу папку. Вариант без флага удалил бы и сам файл. 

$ git rm --cached config.js
rm 'config.js'
$ git commit -m "Remove secret"
[master 3f9a1c2] Remove secret
 1 file changed
 delete mode 100644 config.js

И закрыть путь обратно

Одного git rm --cached мало: следующий же git add . вернёт файл в индекс. Поэтому файл сразу добавляют в .gitignore — тогда Git перестанет его замечать, а сам файл продолжит спокойно лежать на диске.

Если нужно вычистить историю

git rm --cached исправляет только текущее состояние. Чтобы убрать секрет из прошлых коммитов, историю приходится переписать: git filter-repo или BFG, затем принудительная отправка. Всем соавторам после этого нужно переклонировать репозиторий.

В этой симуляции config.js уже лежит в индексе — как будто вы только что приготовили его к коммиту. После git rm --cached он вернётся в рабочую папку с красной меткой «на диске», а коммит закрепит удаление из репозитория.
