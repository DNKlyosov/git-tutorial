Как договариваются о ветках: строгий Git Flow и современный Trunk-Based Development — и как понять, что подходит вашему проекту.

Урок 20. Git в команде

NOTE Зачем это нужно?

В команде важно заранее договориться, как живут ветки. Схема подсказывает, где собирать изменения и когда выпускать релиз, — и помогает не спорить об этом в каждом пулле.

Зачем договариваться о ветках

Ветки — дешёвый инструмент, и именно поэтому команды договариваются, какими ветками пользуются. Схема определяет, где живёт готовая работа, сколько живёт ветка и кто и когда сливает её обратно.

Все схемы — крайние точки одного отрезка: длинные ветки с редкими слияниями или одна ветка с частыми маленькими коммитами.

Классический Git Flow

Появился в 2010 году для продуктов с релизами. Ролей у веток много:

  • main — только релизы, каждая точка истории здесь стабильна.
  • develop — интеграция всех готовых задач.
  • feature/* — одна задача, живёт до вливания в develop.
  • release/* — стабилизация перед выпуском.
  • hotfix/* — срочная правка прямо в main.
main       ●───────────●──────────●     релизы и теги
            ╲         ╱ ╲        ╱
develop      ●──●──●──●───●──●──●       интеграция
                ╲
feature/*        ●──●                   одна задача — одна ветка

Плюсы: строгий порядок, предсказуемые релизы, всегда есть ветка для срочной правки. Минусы: много сущностей, долгие слияния и ощутимый разрыв между работой и main.

Trunk-Based Development

Современная альтернатива: одна долгоживущая ветка (trunk, обычно main), а все изменения попадают в неё короткими порциями — через прямые коммиты или ветки, живущие часы, максимум день.

Чтобы это работало, нужны три вещи: быстрый CI, который проверяет каждый коммит (урок 17), ревью до вливания и feature flags — переключатели, скрывающие недоделанную функциональность.

Плюсы: почти нет конфликтов, релиз можно выпустить в любой момент. Минусы: без автоматизации и флагов всё быстро ломается.

Между ними есть GitHub Flow — компромисс, на котором живёт большинство открытых проектов: одна main, небольшая ветка под задачу, pull request, ревью, merge и удаление ветки.

Что выбрать

  • Частые релизы, сервисы и веб: Trunk-Based или GitHub Flow.
  • Мобильные приложения, игры, продукты с ручной приёмкой: Git Flow с release/*.
  • Библиотеки с поддержкой нескольких версий: долгоживущие ветки версий плюс main.

Главное — не название схемы, а регулярность: короткие ветки, понятные сообщения коммитов, ревью и зелёные проверки. Всё это складывается из простых команд, которые вы уже прошли: git add, git commit, git merge, git tag.

Это финальный урок: новых команд нет, в терминале доступны только help и clear. Дочитайте теорию и нажмите кнопку внизу — откроется поздравление.
