Git умеет запускать ваши скрипты в нужный момент — например, перед коммитом. Так плохой код просто не попадёт в историю.

Урок 17. Хуки Git

NOTE Зачем это нужно?

Хук — это ваш скрипт, который Git запускает автоматически. Он ловит проблему до коммита, пока ошибку ещё дёшево исправить.

Что такое хуки

Хуки (hooks) — это скрипты, которые Git запускает сам в определённые моменты: перед коммитом, после коммита, перед отправкой на сервер. Лежат они в папке .git/hooks и живут только локально: в коммит не попадают и при клонировании не передаются.

pre-commit: проверка до коммита

Самый популярный хук — pre-commit. Git вызывает его в момент git commit, до создания коммита. Если скрипт завершился с ошибкой (ненулевой код выхода), коммит не создаётся, а ваши правки остаются в индексе.

Обычно такой хук проверяет синтаксис, прогоняет линтер и форматтер, ищет случайно закоммиченные пароли и запускает быстрые тесты. Ошибка в самом начале дешевле, чем разбор истории потом.

Как это выглядит

$ touch .git/hooks/pre-commit
$ git commit -m "test"
[Учебная подсказка]: Сработал pre-commit хук. Коммит заблокирован, так как код не прошел проверку.

Коммит не появился, история не изменилась — ровно то, чего мы и хотим от проверки.

Другие полезные хуки

  • commit-msg — проверяет формат сообщения коммита (например, «JIRA-123: ...»).
  • pre-push — запускает тесты перед отправкой ветки на GitHub.
  • post-checkout и post-merge — обновляют зависимости после переключения ветки или слияния.

Почему проверка окупается

Ошибку в коммите потом дорого исправлять: история неизменяема (урок 16), а ветку уже могли забрать коллеги (урок 11). Хук ловит проблему до того, как она разошлась по репозиториям, — это дешёвая страховка для всей команды.

Хуки локальны: у коллеги их может не быть, а обойти проверку можно через git commit --no-verify. Поэтому важные проверки дублируют в CI. В этой симуляции хук — просто файл .git/hooks/pre-commit: пока он есть, коммит блокируется. Файл виден и в рабочей папке — это упрощение ради наглядности.
