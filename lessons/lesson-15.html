Когда в коде появляется странная строка, полезно знать, откуда она взялась. git blame показывает автора, коммит и дату последней правки каждой строки.

Урок 15. Кто это написал

NOTE Зачем это нужно?

История показывает, что менялось, но не отвечает, почему конкретная строка такая. git blame связывает строку с коммитом, автором и датой, чтобы найти решение и его автора.

Зачем нужен git blame

История проекта отвечает на вопрос «что менялось», но не на вопрос «почему вот эта строка такая». git blame показывает по каждой строке файла коммит, автора и дату последней правки.

Задача не в том, чтобы кого-то обвинить, а в том, чтобы найти коммит и обсудить решение с его автором. Часто за странной строкой стоит баг-фикс или требование заказчика.

Как выглядит вывод

Слева от каждой строки — хеш коммита, автор, дата и номер строки, а дальше само содержимое файла: 

7f3a91c4 (Student 2026-10-25 10:00:00 +0300  1) <!DOCTYPE html>
7f3a91c4 (Student 2026-10-25 10:00:00 +0300  2) <html lang="ru">
b41d2aa1 (Student 2026-10-25 11:12:40 +0300  3) <head>
b41d2aa1 (Student 2026-10-25 11:12:40 +0300  4)   <title>Мой проект</title>
0e2c8d17 (Student 2026-10-25 12:30:05 +0300  5) </head>

Строки с одинаковым хешем правил один и тот же коммит — значит, их автор один и тот же человек. Если хеш не менялся с первого коммита, строка живёт в проекте с самого начала.

Полезные варианты

git blame -L 10,20 index.html показывает только строки с 10 по 20 — удобно, когда файл большой. А git blame --ignore-rev <хеш> пропускает коммиты с массовым переформатированием, чтобы не потерять настоящего автора логики.

blame показывает последнего изменившего строку, а не всю историю правок. Чтобы увидеть все изменения строки, используйте git log -L по нужным строкам: в симуляторе он покажет историю целиком.
