rebase и cherry-pick умеют переносить коммиты, а не сливать истории. Разбираемся, как это работает и когда так делать нельзя.

Урок 11. Переписывание истории

NOTE Зачем это нужно?

Иногда ветку удобнее не сливать, а перенести на новую основу. rebase и cherry-pick делают это, но переписывают коммиты — поэтому важно знать ограничения.

git rebase — новая основа для ветки

Ветку можно не сливать с master, а «пересадить» на его актуальную версию. Команда git rebase master, выполненная в ветке feature, берёт ваши коммиты и проигрывает их заново уже поверх свежего master.

В результате получается линейная история: будто вы начали работу ровно с последнего коммита главной ветки. Коммита слияния не появляется, а старые коммиты заменяются копиями — с новыми хешами.

git cherry-pick — один коммит в текущую ветку

Иногда нужен не весь набор изменений, а ровно один коммит. git cherry-pick a1b2c3d копирует коммит a1b2c3d в ветку, где вы сейчас находитесь, — с тем же сообщением, но новым хешем.

Чем это отличается от merge

git merge историю не трогает: старые коммиты остаются как были, а сверху появляется коммит слияния с двумя родителями. По истории видно, когда и что влили, — это честная, но иногда «ветвистая» картина.

git rebase показывает, что происходило в работе, но не показывает, как её объединяли: реального слияния не было. Поэтому историю выбирают по вкусу команды: merge — точность, rebase — чистая прямая линия.

Главное правило: не переписывайте общую историю

Rebase меняет хеши коммитов. Если ветка уже у коллег — после rebase у каждого остаются «старые» коммиты, отличающиеся от ваших, и Git видит две расходящиеся истории.

Дальше — дубли коммитов и конфликты, которые нужно разбирать вручную. Поэтому git rebase нельзя делать в главной ветке (master), если над ней работает команда.

Rebase — для своей локальной ветки, которую больше никто не использует.
